## Implemented and applied

- Booking handoff opens only for the exact current agreed version, while all included travellers still have explicit Ready responses. Creating or assigning responsibilities does not change the trip's planning revision or invalidate agreement.
- Four shared categories cover both overnight stays, local transport, meals, and activities/free time. Each included traveller also has private personal return-travel and activity tasks, independent of their private optional preference. Organisers cannot read or edit another person's personal tasks. The group milestone reveals completion only, without personal methods, budgets or reasons.
- The organiser assigns shared tasks to a member of the agreed included roster. Assigned owners update their own task details and reports. Cross-trip owners, forged actors, unknown provider methods, cross-category methods, stale plan/task/handoff/report revisions and unsupported fields are rejected on the server.
- Methods are explicitly manual verification or a generic IRCTC, Booking.com or GoaMiles search. No listing inventory, quotes, provider account or API integration was added. Provider navigation is an ordinary link with no mutation handler. It cannot mark a task reported. URLs are server-controlled; clients cannot submit arbitrary links or private confirmation data.
- Owners explicitly acknowledge provider checks before saving Booking reported or No reservation needed; these remain self-reported with reporter, timestamp and exact plan/task revision. A link problem keeps the task pending and blocks the prepared-handoff milestone. Changed prices/timing/requirements/other plan terms explicitly reopen review and make earlier agreement historical. New plan versions start fresh tasks with no inherited reports.
- Task definitions, reports and milestone events are append-only. Reassignment preserves prior reports but makes them earlier task reports requiring fresh verification. All existing immutable plans, responses and costs remain intact.
- Five milestones derive from actual saved inputs, feasibility, resolved choices, decision state and handoff details. Handoff prepared requires every shared task and each traveller's private handoff details to have an owner, due time and chosen method; it never means bookings are complete. A postponed/archived trip has no applicable booking milestone. Deferred triggers capture safe progress snapshots after each complete transaction. No historical rows were backfilled; reads do not create records.
